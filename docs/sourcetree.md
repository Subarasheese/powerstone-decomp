## 4. Evidence used for the boundaries

1. **Literal-pool ownership** (certain, interior). SHC puts a file's literals in pools between functions; every function that reads a pool word, every `bsr`/`bra` target and every switch-table target lies in the same object file as the reader. I run a recursive descent from each function (following branches, delay slots and `mova`+`braf/jmp` tables), take every `mov.l/mov.w @(disp,pc)` pool address and every `bsr`/`bra`/conditional-branch target, find the function that contains it, and union the whole interval of functions between reader and target (an object file is contiguous). Result: 4991 functions plus 612 unlisted entries form 1080 cells; no pool, bsr or bra crosses a cell boundary.
2. **Unlisted functions**: `functions.txt` misses a lot of code. The descent therefore also covers 612 unlisted entry points: 294 from `tools/1-2-baseline/missed_funcs.py` (kept only if they decode as plausible code and do not sit on bytes that real code reads as pool words) and 318 found by a sweep of the unexplained gaps (prologue-like start, terminates in rts/bra/jmp, chained from the end of the previous function and its pool). 92 cells consist only of such unlisted code (probably whole files or file parts); because rows must start at a function of `functions.txt` they are folded into the preceding row, which is why some rows carry `hidden_funcs_unlisted` > 0 and large `unexplained_bytes`. The proposed additions are in `docs/missed_functions.txt` (functions.txt itself is untouched).
3. **Alignment**: object sections start 4-aligned, function starts inside a file are only 2-aligned (40% of the function starts inside cells are 2 mod 4; after the merge 0% of the row starts are). A cell that starts at 2 mod 4 is therefore merged into its predecessor (68 merges). Of the remaining 4-aligned cell starts about 87% are expected to be true file starts (estimated from the 4-aligned share of cell starts, 92%, versus 60% for interior starts).
4. **SDK source names** (`sdk-source/` headers): all 17 original files that the SDK source covers (adx_bsc.c, adx_crs.c, adx_errs.c, adx_fs.c, adx_rnas.c, adx_tsvr.c, adx_xpnd.c, lcdvms.c, vmsapi.c, mw_rnaer.c, sj_utl.c, memcpy.c, memset.c, strcpy.c, strlen.c, strncpy.c, acosf.c) land in exactly one row each, and no row contains functions of two source files. This is the independent check of the cell method (17/17 agree, including adjacent files with no pool at all, e.g. memcpy.c|memset.c|sprintf|strcpy.c|strlen.c).
5. **Banner / string / function-name groups**: ADX (E81012xx messages, ADXT/ADXF/ADXSTM/ADXSJD/ADXB/ADXPD/ADXRNA/ADXERR/ADXCRS names), mwRna/mwSnd (E12xx messages), gdFs (CD001, "(no device)"), Kamui ("KAMUI", "EnableTexture16MB", "RENDER"), KATANA_FLASH, libsnd0.77/DTPK/SPSD, AM2 driver blob, VMS save names, test-menu and debug-menu texts. These name a file and set its layer; where two neighbouring rows carry different library names the boundary is marked certain.
6. **Hand-written assembly**: the entry stub and cache ops (ocbp/ocbi), control-register and FPU-bank code (ldc/stc sr,gbr,vbr,ssr..., frchg/fschg) are flagged `asm_like=yes` (74 rows); a boundary next to such a row is marked certain only for cache ops/rte/trapa.
7. **16-byte alignment**: 0C0E0790-0C0E5178 and 0C0FBA80-0C0FC360 consist of functions padded to 16 bytes with `nop` and no pools, i.e. a different compiler setting (-align16 or another toolchain). They are assigned to the sound-driver wrapper layer (NAOMI/nl, guess); their file boundaries are not determinable and every function is its own row (guessed).
8. **Boundary classes**: *certain* = two distinct SDK-source/named library files meet, or a hand-asm/anchored-layer change; *probable* = no link crosses, start is 4-aligned and the previous row ends with a pool/padding tail (expect roughly 85-90% to be real file starts; a wrongly split file is harmless for matching because a cut after a pool dump leaves the compiler in an empty state); *guessed* = no link crosses but the previous row has no pool tail (a run of pool-less functions, ambiguous by nature, e.g. runs of 4-byte `rts` stubs).

## 6. Problems and open points

### 6.1 Data misdetected as functions (18 entries, all after the code)
`functions.txt` lists 18 entries at or above 0C159FB0 that are data: 0C159FB0 (38 bytes, inside the string area), 0C17FD70 (2028 bytes; a table of 32-bit pointers to data at 0C11xxxx), and 16 four-byte entries at 0C32AE34-0C3371F4 (pointer tables, e.g. `bra`-looking words that are 32-bit addresses). The real code ends at about 0C1161C0 (end of `FUN_0C115FB8`); everything after is data (1.9 MB: file-name tables from 0C116198, credits text, ADX/model tables, library banners such as "syStart Ver 1.07", "Shinobi Ver 1.42", "ADXT Ver.5.32"). They form the three `data_*` rows. Because rows must start at a function address, the rows before them cannot end where their code ends; the last code row (`0c115fb8`) therefore spans 0C115FB8-0C159FB0 in the csv but its `bytes` stops at 0C1161C0.

### 6.2 Entry stub outside any function
0C010000-0C010028 is the program entry (clears RAM at 8C00C000-8C00F400, calls 0C010038/0C010028, jumps to the game main `sys_main_loop`); it is not an entry of `functions.txt` (asm/0c010000_blob). It shares its literal pool (0C010064-0C010090) with `FUN_0c010038`, so it belongs to the first row (crt0).

### 6.3 Entries that look like labels, not functions
155 functions are reached only by `bra` from another function in the same file and are never called, pointed at, or the target of a `bsr` (shared epilogues, switch-case tails, tail-merge targets that the analysis split off). They are not independent functions; matching them needs the enclosing function. Full list: `docs/problems_labels.txt`. A further 862 functions have no inbound reference at all (no pool or data word holding the address, no bsr; this includes the label-like ones above): callbacks reached through computed addresses, shared code reached by fall-through/bra, or dead code.
Also: 57 entries whose recorded size is larger than the distance to the next entry (overlaps, up to 2816 bytes: e.g. `fx31_mode_attack` 3098 bytes vs. next entry at +282, `FUN_0c02e438`, `menu_stage_select_scene_update`), i.e. the next entry lies inside the first; and 66 functions whose control flow runs beyond the next entry (switch-case blocks listed as functions, e.g. `FUN_0c01e860`, `pl_jack_state_update`, `pl_gunrock_state_update`, `ui_draw_challenger_info`). `tools/boundaries.py` can re-cut these.

### 6.4 Code the analysis did not list (unlisted functions)
`missed_funcs.py` reports 759 candidates; 347 are in the data area (pointer tables, ignore), 412 are inside the code range and 294 of them decode as plausible code that is not pool data. A sweep of the remaining unexplained gaps (see section 4) finds 318 more entry points, chained one after another (e.g. 16 consecutive functions in 0C07515C-0C07660C, 6 in 0C088290-0C08975C). Together 612 unlisted functions, forming 92 cells of their own (whole files or file parts). They are listed in `docs/missed_functions.txt` as `F <addr> 0 FUN_<addr>` proposals (size 0: run `tools/boundaries.py` to size them). They sit inside the gap of the preceding entry, so a unit that ends at the next listed entry silently contains them, and the row of that entry is larger than its real source file. Rows that contain unlisted code: 171. This is the largest weakness of the map: file starts that coincide with unlisted functions cannot be reported until they are added to functions.txt.

### 6.6 Boundaries that could not be decided
- 87 row starts are *guessed* (the previous row has no pool tail, so nothing but alignment separates the two). They fall into 66 runs; the longest: 0c07c3ea x5, 0c085606 x5, 0c0fb464 x4, 0c0e7038 x3, 0c108b48 x3, 0c010138 x2, 0c06208c x2, 0c076d98 x2.
- The 16-aligned sound-wrapper regions (0C0E0790-0C0E5178 and 0C0FBA80-0C0FC360) are one row per function; the real files are probably larger (unknowable without pools).
- *probable* starts (758) are cuts at which no pool, bsr, bra or table crosses; roughly 10-15% of them are expected to be mid-file pool dumps of a larger file. SHC dumps a pool mid-file whenever a function end is reached with enough pending literals (observed dumps after 200-700 bytes of pending code, also forced by switch tables), so a mid-file dump cannot be told from an end-of-file dump from the code alone. This is harmless for matching (a split at a pool dump compiles identically), but means the "files" column may over-count.
- Existing units that cross my rows: `w0_u_empty1.c` 0c010134-0c010160 spans rows 0c010134,0c010138,0c01013c,0c01015c; `w2_u_vec1.c` 0c062050-0c0620a4 spans rows 0c062050,0c06208c; `w3_u_f084168.c` 0c084168-0c084304 spans rows 0c084168,0c08417c; `w5_u_libc.c` 0c0e7178-0c0e71d4 spans rows 0c0e7178,0c0e71bc. All four join pool-less adjacent functions (two of them memcpy.c and memset.c, known separate files), so they show that adjacent pool-less rows can be compiled together without changing bytes; they do not prove a common file.
- `thunk_FUN_*` entries (6-byte `mov.l pool,r3; jmp @r3` stubs, 28 of them in adx_rnas.c) are probably compiler-generated tail-call wrappers; they are counted as normal functions.
- Layer names: only the ADX/mw/gdFs/bu/pd/Kamui banners and error strings are firm; NAOMI/nl is assigned to the AM2/AICA sound-driver client code (libsnd 0.77, DTPK/SPSD, 16-aligned command stubs) and is a guess (no function in `functions.txt` carries an `nl*` name). The Game layer contains everything unanchored, including code that may belong to Capcom's own engine libraries.
